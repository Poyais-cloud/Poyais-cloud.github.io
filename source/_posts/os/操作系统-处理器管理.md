# 第二章 处理器管理

> **前情提要**
> 第一章我们学了**操作系统的总体结构**——它是用户与硬件之间的资源管理者。本章把"资源"具体化为最重要的那一种：**CPU（处理器）**，并引出整门 OS 课最核心的对象：**进程**。
> 后面第三章讲存储管理、第四章讲设备管理、第五章讲文件系统，但调度、互斥、同步、死锁这些"并发问题"会一直伴随到整门课结束。**本章是 OS 全课的脊梁。**

> **本章统一类比：自习室模型**
> 为便于理解，本章使用**自习室类比**贯穿始终：
>
> | OS 概念 | 自习室类比 |
> |---------|-----------|
> | **CPU** | 单人间自习室（一次只能一人用） |
> | **进程** | 自习室名额（资源拥有者） |
> | **单线程进程** | 名额里只有一个人 |
> | **多线程进程** | 名额里多个人共用（挤在一起） |
> | **线程** | 自习室里的人（实际执行者） |
> | **资源** | 笔、黑板、座位等 |
> | **PCB** | 学生的档案袋（记录学到哪了） |
> | **就绪队列** | 排队等自习室的学生 |
> | **等待队列** | 等笔、等座位的学生 |
> | **信号量** | 笔筒（S = 笔的数量） |
> | **P 操作** | 借笔，没笔就等 |
> | **V 操作** | 还笔，有人等就通知 |
> | **时间片** | 每人最多用 10 分钟 |
> | **临界区** | 用黑板的那段时间 |
> | **互斥** | 一次只能一人用黑板 |
> | **死锁** | 每人拿一支笔等另一支 |

> **核心概念：什么是"资源"？**
> **资源 = 进程运行所需要的任何东西**
>
> **资源分类**：
> | 类别 | 例子 |
> |------|------|
> | **硬件资源** | CPU、内存、磁盘、打印机、网卡 |
> | **软件资源** | 文件、信号量、消息队列、共享内存、锁 |
> | **信息资源** | 共享变量、缓冲区、数据库连接 |
>
> **资源的关键属性**：
> | 属性 | 分类 | 例子 |
> |------|------|------|
> | 可抢占性 | 可抢占 vs 不可抢占 | CPU/内存 vs 打印机/锁 |
> | 独占性 | 独占 vs 共享 | 打印机 vs 内存/只读文件 |
> | 持久性 | 永久 vs 临时 | CPU/内存 vs 消息/信号量 |
>
> **资源与进程状态的关系**：
> ```
> 就绪 → 执行     = 获得 CPU 资源
> 执行 → 就绪     = CPU 被抢占
> 执行 → 等待     = 等待某资源（I/O、锁、信号量）
> 等待 → 就绪     = 资源到位
> ```

## 2.1 程序的顺序执行和并发执行

### 2.1.1 顺序执行

> 一句话定义
> 一个程序的若干程序段必须**严格按规定次序前后相继**地执行，前一段结束后一段才能开始——这叫**顺序程序**。它是个**静态概念**。

**三大特点**：

| 特点 | 含义 |
|---|---|
| **顺序性** | 处理器严格按程序规定的次序执行 |
| **封闭性** | 程序运行时独占机器资源，结果不受外界因素影响 |
| **可再现性** | 结果只与初始条件有关，与执行速度（时间）无关 |

### 2.1.2 并发执行

> 为什么要并发
> 顺序执行下 CPU 和外设大量时间在互相等（如 I/O 时 CPU 闲、计算时 I/O 闲）。**并发**就是让多个程序在时间上**重叠**地推进，提高资源利用率。

**经典图示**：每个程序段由"输入 i / 计算 c / 输出 p"三步组成，系统中有 1 输入单元、1 计算单元、1 输出单元，3 个程序并发：

```text
时间 →
输入: i1 → i2 → i3
计算:    → c1 → c2 →  c3
输出:           → p1 →  p2 →  p3
                 ↑
              i2 与 c1 同时进行
              c2 与 p1 同时进行
```

可以看出：i2 与 c1 同时执行，c2 与 p1 同时执行——三个硬件单元同时在干活，比顺序执行快了一倍多。

> 学术延伸
> - 操作系统领域的并发叫 **Concurrency**
> - 计算机体系结构里的并发叫 **Pipeline**（指令级并发，流水线作业）

**并发执行的两类**：

1. **多道程序并发**：多个独立程序同时被装入主存，互相穿插执行（**程序之间的并发**）
2. **程序内部并发**：同一程序中可同时或乱序执行的代码段（**程序内部的并发**），例如：
   ```text
   read(a);
   read(b);    -- 两条读语句之间不依赖, 可并发
   ```

### 2.1.3 并发 vs 并行（必考辨析）

> 高频概念混淆
> - **并发**：宏观上同时，微观上交替——单 CPU 上多进程"轮着用"
> - **并行**：物理上真正同时——多 CPU / 多核同一瞬间多个进程在跑
>
> 课件用了 Go 语言的金花鼠比喻：
> - **一个**书堆/火炉 + 多只鼠 → 鼠们必须**轮流**取书烧书，其余处于挂起 → **并发**
> - **多个**书堆/火炉 + 多只鼠 → 鼠们各干各的，互不抢占硬件 → **并行**

并发 ≠ 并行，并行 ⊂ 并发。Go 之父 Rob Pike 那只地鼠 Gordon 是这个比喻的来源（顺带：Pike 还参与开发了 UTF-8）。

### 2.1.4 并发的复杂性（必考三件套）

> 顺序执行的"封闭、可再现"在并发下全没了
> 并发引入三个新麻烦：

| 复杂性 | 含义 |
|---|---|
| **间断性** | 进程互相制约，执行节奏变成"执行—暂停—执行" |
| **失去封闭性** | 多进程共享资源，资源状态被多家修改，运行不再独立 |
| **不可再现性** | 同样的输入，因调度顺序不同得到不同结果（**非确定性 Non-Deterministic**） |

#### 不可再现性的经典反例

两进程共享变量 N：

```text
Procedure A {                Procedure B {
    N := N + 1;                  Output(N);
}                                N := 0;
                             }
```

三种不同交错执行序列：

**情形 1**：A 先完成，再 B

| 顺序 | 操作 | 结果 |
|---|---|---|
| 1 | (A) N := N + 1 | N = N+1 |
| 2 | (B) Output(N) | 输出 N+1 |
| 3 | (B) N := 0 | N = 0 |

**最终：输出 N+1，N = 0**

**情形 2**：B 先完成，再 A

| 顺序 | 操作 | 结果 |
|---|---|---|
| 1 | (B) Output(N) | 输出 N |
| 2 | (B) N := 0 | N = 0 |
| 3 | (A) N := N + 1 | N = 1 |

**最终：输出 N，N = 1**

**情形 3**：B 的两条语句被 A 切开

| 顺序 | 操作 | 结果 |
|---|---|---|
| 1 | (B) Output(N) | 输出 N |
| 2 | (A) N := N + 1 | N = N+1 |
| 3 | (B) N := 0 | N = 0 |

**最终：输出 N，N = 0**

> 三种交错，三种结果
> 同样的初始 N，居然得到三个不同的最终状态——这就是**不可再现性 / 非确定性**。
> 这正是 OS 顶会 **OSDI**（Operating Systems Design and Implementation）和 **SOSP**（Symposium on Operating Systems Principles）反复研究的核心问题。

## 2.2 进程的概念

### 2.2.1 为什么需要进程

> 程序 → 进程的认知升级
> 用"程序"只能静止地、孤立地分析一段代码；用**进程**才能动态地刻画"执行中的程序"——它有状态、有资源、有生命周期。

#### 编译程序例子

编译程序 P 只有一份，源代码有甲、乙两个：

**单进程版本**（顺序编译）：

```text
Procedure 编译(源程序) {
    编译(甲);
    编译(乙);
}
-- 1 个进程, 串行处理
```

**多进程版本**（并发编译）：

```text
Procedure 编译(源程序) {       Procedure 编译(源程序) {
    编译(甲);                       编译(乙);
}                              }
-- 进程 P甲                     -- 进程 P乙
-- 2 个进程, 可并发
```

> 思考题
> 1. **单 CPU 环境下**，单进程编译 vs 多进程编译，谁性能更好？
> 2. **多核环境下**呢？
> 3. 为什么？
>
> 提示：单 CPU 下多进程会有**上下文切换开销**，可能反而慢；多核下多进程能真并行 → 快。

**结论**：同一个程序在不同数据集上的执行 = 不同的进程。在多道程序设计技术系统中，"进程"概念是必须的。

### 2.2.2 进程的经典定义（四家之言）

| 出处 | 定义 |
|---|---|
| Madnick & Donovan（MIT） | 进程是可以并发执行的计算部分 |
| Cohen & Jefferson（CMU） | 进程是一个独立的、可以调度的活动 |
| P. J. Denning（斯坦福） | 进程是一个抽象实体，执行任务时分配/释放各种资源 |
| Dijkstra（UT Austin） | 进程是一系列逐一执行的操作，操作的确切含义有赖于描述详尽程度 |

### 2.2.3 进程的工作定义与特性

> 课本定义（必背）
> **进程 = 可并发执行的程序在一个数据集上的一次执行过程，是系统进行资源分配的基本单位。**

**五大特征**：

| 特征 | 含义 |
|---|---|
| **动态性** | 由创建产生、由调度执行、因等待暂停、由撤销消亡——有生命期 |
| **并发性** | 多个进程实体同存于主存中，能在一段时间内同时运行 |
| **独立性** | 是独立运行、独立获得资源、独立调度的基本单位 |
| **异步性** | 各进程按各自不可预知的速度推进（→ 不可再现性的根源） |
| **结构特征** | 由"程序段 + 数据段 + PCB"三部分组成，三者合称**进程映像 / 进程上下文** |

> 进程 vs 程序
> - 程序是**静态代码**，进程是**动态执行过程**
> - 一个程序可以对应多个进程（不同数据集）
> - 进程有生命周期，程序不会"死"

### 2.2.4 进程的基本状态（三态模型）

> 三态铁三角
> 进程总是处于以下三态之一：

| 状态 | 含义 |
|---|---|
| **就绪** | 已得到除 CPU 外所有资源，只等被调度。同时可有多个就绪进程，组织成**就绪队列** |
| **执行** | 已获得 CPU 正在执行；**单 CPU 系统同一时刻只有一个**；多 CPU 系统可有多个 |
| **等待** | 因等 I/O、缓冲、消息等事件而暂停，必须等到事件结束才能回到就绪。组织成**等待队列**（可按等待原因分多个） |

**状态转换**：
- 就绪 → 执行：进程调度
- 执行 → 就绪：中断/时间片到（被动）
- 执行 → 等待：出现等待事件（主动）
- 等待 → 就绪：等待事件结束
- 执行 → 结束：进程完成

> 什么是"原语"？
> **原语** 是操作系统内核中由若干条指令组成的**原子操作**——它们在执行过程中**不可被中断**。
>
> **为什么需要原语？** 在多进程/多线程环境下，如果操作能被打断，可能导致数据不一致或状态混乱。原语保证了操作的**完整性**：
> ```
> 普通操作（可被中断）：
>   进程A: 读取变量 → [被打断] → 进程B修改了变量 → 进程A继续（数据已不一致！）
>
> 原语操作（不可中断）：
>   进程A: 读取 → 修改 → 写入（一气呵成，中间谁也不能插手）
> ```
>
> **常见的进程控制原语**：
> | 原语 | 作用 |
> |------|------|
> | `创建原语` | 创建新进程 |
> | `撤销原语` | 终止进程 |
> | `阻塞原语` | 主动让进程从"执行"变为"等待" |
> | `唤醒原语` | 把等待中的进程变为"就绪" |

> 状态转换的非对称性
> - 等待 → 执行：**不存在**（等到事件后只能进就绪队列再排队）
> - 执行 → 等待：是进程**自己主动**调阻塞原语
> - 执行 → 就绪：是被**强制剥夺**（中断/时间片到）

### 2.2.5 进程控制块（PCB）

> 一句话
> **PCB（Process Control Block）= 操作系统用于记录和刻画进程状态及有关信息的数据结构。**
> OS 对并发进程的所有控制和管理都依据 PCB 进行——**有 PCB 才有进程**。

> PCB = 进程的"档案袋"
> 想象你是**教务处主任（操作系统）**，要管理全校学生（进程）。每个学生有一个档案袋：
> ```
> ┌─────────────────────────────────────┐
> │           学生档案袋 (PCB)            │
> ├─────────────────────────────────────┤
> │ 学号: 2024001              ← pid    │
> │ 姓名: 张三                 ← 进程名  │
> │ 状态: 在教室上课           ← state   │
> │ 年级: 大二                 ← 优先级  │
> │ 班主任: 李老师             ← parent  │
> │ 课程表: 高数、英语...      ← 程序代码 │
> │ 当前进度: 高数第3章        ← 现场信息 │
> └─────────────────────────────────────┘
> ```
>
> **为什么需要 PCB？** CPU 就像一个**单人间自习室**，一次只能进一个人：
> - 学生A 时间到被赶出来 → 教务处把"学到哪了"记入档案袋（保存现场）
> - 学生B 进去学习 → ...
> - 学生A 再次进入 → 教务处看档案袋："哦，你上次学到第3章，继续"
>
> **没有 PCB 会怎样？** 进程被切换时忘了执行到哪，下次从头开始 → 全乱套。

**PCB 的四类信息**：

| 类别 | 内容举例 |
|---|---|
| **标识信息** | 进程 ID（唯一标识符） |
| **说明信息** | 进程类型、状态、优先级 |
| **现场信息** | 让出 CPU 时保存的 PSW、通用寄存器 |
| **管理信息** | 调度参数、资源清单、亲属关系 |

**PCB 的关键工程要点**：

- 创建进程时**建立** PCB，进程结束时**回收** PCB
- PCB 被**频繁访问**（调度、中断、监督），故必须**常驻主存**
- 系统把所有 PCB 组织成**链表**，存于专门的 PCB 区

#### 实例：Linux 的 PCB

Linux 中 PCB 是 **`struct task_struct`**（在 3.12 版内核里位于 sched.h，约第 1019~1410 行）：

```c
struct task_struct {
    volatile long state;             // 进程状态 (-1 不可运行, 0 可运行, >0 已停止)
    void *stack;                     // 进程内核栈
    pid_t pid;                       // 进程标识符
    pid_t tgid;                      // 线程组 ID
    struct task_struct *parent;      // 父进程
    struct list_head children;       // 子进程链表
    struct mm_struct *mm;            // 内存管理信息
    struct files_struct *files;      // 打开的文件
    struct signal_struct *signal;    // 信号处理
    // ... 还有几百个字段 ...
};
```

> 核心字段速记
> | 字段 | 作用 | 备注 |
> |------|------|------|
> | `state` | 进程状态 | `volatile` 防优化，可能被其他 CPU/中断修改 |
> | `stack` | 内核栈指针 | 用户态→内核态切换时使用 |
> | `pid` | 唯一标识符 | `ps`、`kill` 用的就是这个 |
> | `tgid` | 线程组 ID | 同一进程的所有线程共享，用户态看到的"进程 ID" |
> | `parent` | 父进程 PCB | 形成进程树，子进程结束向父进程发 `SIGCHLD` |
> | `children` | 子进程链表 | 双向循环链表，遍历所有子进程 |
> | `mm` | 地址空间 | 页表、代码/数据/堆/栈位置；线程间共享 |
> | `files` | 文件描述符表 | `fd` 0/1/2 = stdin/stdout/stderr |
> | `signal` | 待处理信号 | `kill` 命令写入，调度时检查处理 |
>
> **设计哲学**：Linux 的进程、线程、内核任务**统一用 `task_struct`** 表示——"一切皆任务"，简化调度逻辑。

### 2.2.6 进程队列

> 同状态进程组队
> 把处于**相同状态**的进程链接起来 → "进程队列"。链接载体就是 PCB。

| 队列类型 | 包含 |
|---|---|
| **就绪队列** | 所有就绪态进程，可能多个（按优先级分） |
| **等待队列** | 所有等待态进程，常按等待原因再分多个 |

**两种组织方式**：

#### 方式 1：链表方式

```text
就绪队列头 → PCB1 → PCB2 → PCB3 → NULL
等待队列头 → PCB4 → PCB5 → NULL
执行指针 → PCB6
```

#### 方式 2：索引方式

```text
执行指针 ──────→ PCB6

就绪索引1 ──→ PCB1
就绪索引2 ──→ PCB2

等待索引1 ──→ PCB3
等待索引2 ──→ PCB4 ──→ PCB5
```

索引方式可针对不同优先级、不同等待原因开多个索引，查找快但维护开销大。

## 2.3 进程控制

### 2.3.1 什么是原语

> 原语 = 原子操作
> **原语= 一组系统命令，具备原子特性——要么全部执行，要么不执行，不存在"执行一半"的中间状态。**
>
> 进程相关四大控制原语：**创建、撤销、阻塞、唤醒**。
> （不存在"进程创建一半"的说法）

> 四原语速览
> | 原语 | 谁调用 | 状态变化 | 核心动作 |
> |------|--------|----------|----------|
> | **创建** | 父进程 / OS | 无 → 就绪 | 建 PCB、分配资源、入就绪队列 |
> | **撤销** | 父进程 / 自己 / OS | 执行/就绪/等待 → 无 | 回收资源、删 PCB、级联撤销子孙 |
> | **阻塞** | **自己** | 执行 → 等待 | 保存现场、改状态、入等待队列、触发调度 |
> | **唤醒** | **其他进程** | 等待 → 就绪 | 移出等待队列、入就绪队列 |

### 2.3.2 进程的创建

**调用方**：
- 系统初启时由 OS 创建系统进程
- 用户作业被作业调度程序调入时为它创建进程

**创建原语的核心任务**：**建立 PCB 并填入有关参数**。复杂场景还要提供资源清单。

**创建逻辑**：

```text
申请空闲 PCB
   ↓
PCB 池有空? ──No──→ 系统资源耗尽, 创建失败
   ↓ Yes
分配资源
   ↓
填写 PCB (标识/状态/资源/优先级 ...)
   ↓
插入就绪队列
   ↓
返回
```

> 资源耗尽怎么办：OOM Killer
> Linux 的处理方式是 **OOM Killer（Out Of Memory Killer）**——当系统内存耗尽时，**自动选择并杀死**占内存最多/最近最少使用的进程，释放资源。
> 这是 Linux 的"兜底机制"，但被杀的进程会丢失所有未保存数据。

### 2.3.3 进程的撤销

进程结束的几种情形：
1. 正常完成工作而终止
2. 因错误异常终止
3. 被祖先进程要求终止

**撤销原语要做的事**：

```text
PCB_ADDR → OLD_PCB           # 取要撤销的 PCB
   ↓
从所属系统队列中移出 OLD_PCB
   ↓
释放并归还所有系统资源
   ↓
检查是否有子孙进程
   ↓
有 ──→ 递归调用撤销原语撤销子孙
   ↓
撤销 OLD_PCB
```

### 2.3.4 进程的阻塞与唤醒

| 操作 | 触发者 | 状态变化 |
|---|---|---|
| **阻塞** | 进程**自己**调用阻塞原语 | 执行 → 等待 |
| **唤醒** | **其他进程**调用唤醒原语 | 等待 → 就绪 |

> 关键对称性破缺
> - **阻塞**：进程**自己**调用，主动让出 CPU
> - **唤醒**：**别的进程**调用，被动被拉起
> - 为什么不能自己唤醒自己？因为自己在等待状态，**没有 CPU 执行任何代码**！

**阻塞原语流程**：

```text
中断处理器
   ↓
保存 CPU 现场 → 当前进程 PCB 现场区
   ↓
置进程状态为 "等待"
   ↓
插入相应等待队列
   ↓
转进程调度程序, 另选一个进程投入运行
```

**唤醒原语流程**：

```text
找到等待队列中的目标进程 PCB
   ↓
移出等待队列
   ↓
置进程状态为 "就绪"
   ↓
插入就绪队列
   ↓
返回（调用者继续执行）
```

> 经典误区
> "等待 → 执行" **不存在**！被唤醒的进程只能进就绪队列，再次经过调度才有机会执行。

## 2.4 进程调度

### 2.4.1 为什么需要调度

> 一句话
> CPU 在**任一时刻只能让一个进程占用**，而就绪队列里通常**有多个进程**。如何决定让谁先用？这就是进程调度。

### 2.4.2 调度的主要功能

1. **记录**系统中所有进程的执行情况（依靠 PCB）
2. **选择**占有 CPU 的进程（按某种策略从就绪队列中挑）
3. **分配** CPU——把选中进程的 PCB 现场信息送入处理器寄存器（**进程上下文切换**）
4. **收回** CPU——把处理器寄存器内容写回 PCB

### 2.4.3 调度的时机（必考"7个情况"）

> 期末填空高频
> 进程调度发生在以下 7 种情况：
> 1. 正在执行的进程**执行完毕**
> 2. 执行中的进程调用阻塞原语**自我阻塞**
> 3. 调用 P 原语**因资源不足被阻塞**，或调用 V 原语激活了等待队列
> 4. 提出 **I/O 请求**后被阻塞
> 5. 分时系统中**时间片用完**
> 6. 执行完系统调用**返回用户进程**时
> 7. 可剥夺方式下，**就绪队列出现优先级更高**的进程

### 2.4.4 四大调度算法（必考重头戏）

#### (1) 先来先服务 FCFS（First Come First Served）

按进入就绪队列的先后顺序选择，**非抢占**。一旦占有 CPU，就一直执行直到完成或主动让出。

| 优点 | 缺点 |
|---|---|
| 原理简单，实现简单 | 长进程影响短进程的等待时间（"短作业饥饿"） |

##### FCFS 实例分析一

三个进程 A(3ms)、B(3ms)、C(24ms)，到达顺序 **A → B → C**：

| 进程 | 到达时刻 | 服务时间 | 开始时刻 | 完成时刻 | 等待时间 |
|---|---|---|---|---|---|
| A | 0 | 3 | 0 | 3 | **0** |
| B | 0 | 3 | 3 | 6 | **3** |
| C | 0 | 24 | 6 | 30 | **6** |

总等待时间 = 0 + 3 + 6 = 9 ms
**平均等待时间 = 9 / 3 = 3 ms**

##### FCFS 实例分析二

同样三个进程，但到达顺序 **C → A → B**：

| 进程 | 到达时刻 | 服务时间 | 开始时刻 | 完成时刻 | 等待时间 |
|---|---|---|---|---|---|
| C | 0 | 24 | 0 | 24 | **0** |
| A | 0 | 3 | 24 | 27 | **24** |
| B | 0 | 3 | 27 | 30 | **27** |

总等待时间 = 0 + 24 + 27 = 51 ms
**平均等待时间 = 51 / 3 = 17 ms**

> FCFS 对到达顺序极其敏感
> 同样三个进程，仅仅因为到达顺序不同，平均等待时间从 3ms 飙到 17ms（**5 倍多**）。这是 FCFS 最大的弱点——**长作业先到，会拖累所有短作业**。

#### (2) 优先数调度

每个进程分配一个优先数，调度时**让优先数最高的进程先用 CPU**。优先数相同则按 FCFS。

**优先数确定方式**：

| 方法 | 特点 |
|---|---|
| **静态法** | 进程开始执行前确定，期间不变。简单、开销小，但效率低 |
| **动态法** | 结合静态特性 + 运行时动态调整。开销大但调度性能更好 |

**抢占性**：

| 方式 | 含义 |
|---|---|
| **非抢占式** | 高优先数进程占 CPU 后一直执行直到主动让出 |
| **可抢占式** | 任何时刻都让最高优先数进程在 CPU 上运行——更高优先级到来立刻夺权 |

**动态优先数确定的两条经典准则**：

> **准则 1**：提高经常使用外围设备的进程的优先数，有利于利用 CPU 与外设的并行能力
>
> 解读：
> - "经常使用外设"：意味着该进程 **CPU 占用时间少、I/O 占用时间长**（典型 I/O 密集型）
> - "提高优先数"：让 I/O 密集型进程被优先调度，迅速做完 I/O 操作
> - "并行能力"：之后 CPU 空闲，让计算密集型进程占用，**两类进程的工作互相重叠** → 提高吞吐量
>
> **准则 2**：提高较长时间未使用 CPU 的就绪进程优先数 → 缩短平均等待时间，**防止饥饿**
>
> 解读：
> - 让"等了很久"的进程优先被调度 → 防止某些进程永远排不到

#### (3) 时间片轮转

把 CPU 时间切成固定大小的**时间片**，就绪队列按 FIFO 排队，每次给队首一个时间片：
- 时间片用完未结束 → 重新排到**队尾**
- 时间片内发生等待事件 → 排到**等待队列**，事件结束再回就绪队尾

> 直观理解：两条队列
> ```
> 就绪队列（只差 CPU）：  [P1] → [P2] → [P3] → ...
>                                  ↑
>                              队头执行中
>
> 等待队列（缺其他资源）：  [P4] → [P5] → ...   （等 I/O、等锁等）
> ```

##### 时间片轮转实例

设有 3 个进程，所需 CPU 时间分别为 7、4、9 个时间单位（**右边先到**），时间片 = 4。

**初始就绪队列**（右边先到达）：

```text
[ 9 | 4 | 7 ] ←队首
```

**第一轮调度**：每个进程跑一个时间片（4 单位）

| 进程 | 已用 | 剩余 | 操作 |
|---|---|---|---|
| 7 → 7-4 | 4 | 3 | 时间片到, 排队尾 |
| 4 → 4-4 | 4 | 0 | **完成!** |
| 9 → 9-4 | 4 | 5 | 时间片到, 排队尾 |

第一轮后队列状态：`[ 5 | 3 ]`

**第二轮调度**：

| 进程 | 已用 | 剩余 | 操作 |
|---|---|---|---|
| 3 → 3-3 | 3 | 0 | 不到时间片就完成 |
| 5 → 5-4 | 4 | 1 | 时间片到, 排队尾 |

第二轮后队列状态：`[ 1 ]`

**第三轮调度**：

| 进程 | 已用 | 剩余 | 操作 |
|---|---|---|---|
| 1 → 1-1 | 1 | 0 | **全部完成！** |

##### 时间片长度 q 的选择（必考公式）

$$ q = \frac{R}{N} $$

- R：系统对响应时间的要求
- N：进程数

> 时间片长度的两难
> - q **太短** → 上下文切换次数多，系统开销大
> - q **太长** → 退化为 FCFS

#### (4) 多级反馈队列

> 综合上面三种的"集大成者"
> 设置**多个就绪队列**，优先级递减，**时间片递增**：高优先级队列时间片小，低优先级队列时间片大。

**结构示意**：

```text
队列 1 (优先级最高, 时间片 = 1q)  ──→ CPU
队列 2 (优先级次之, 时间片 = 2q)  ──→ CPU
队列 3 (优先级再次, 时间片 = 4q)  ──→ CPU
...
队列 n (优先级最低, 时间片 = 2^(n-1) q) ──→ 时间片轮转
```

**调度规则**：

1. 调度从**第 1 队列**开始，按 FCFS 选当前队列的进程
2. 时间片内未完成 → 进入**下一队列队尾**
3. 仅当第 1~(i-1) 队列**全空**时，才会调度第 i 队列
4. 处理 i 队列时，若高优先级队列**新来进程** → 抢占 CPU，被抢者放回**第 i 队列队尾**

**性能优势**：

- **短作业**：在前几个高优先级队列内就完成 → 周转时间短
- **交互作业**：第 1 队列内即可响应 → 用户体验好
- **长作业**：依次降到底层后**轮转执行** → 不会无限饥饿

## 2.5 线程

### 2.5.1 为什么需要线程

> 进程的两个角色被拆分
> 传统进程同时承担**资源拥有**和**调度执行**两个角色，导致创建、切换、管理开销巨大。
> **现代操作系统把这两个角色拆开**：
> - **进程** = 资源申请与拥有的单位
> - **线程** = 调度执行的基本单位

### 2.5.2 线程的概念

> 一句话定义
> 线程是进程中的一个实体，是**可独立参与调度的基本单位**。一个进程可以有 1 个或多个线程，它们**共享**所属进程拥有的资源。

线程自己只拥有运行时**必不可少的少量资源**：程序计数器、一组寄存器、栈。

### 2.5.3 线程的属性（七条，常考填空）

1. 多个线程可**并发执行**
2. 一个线程可**创建另一个线程**
3. 线程具有**动态性**，从创建到衰亡有生命周期
4. 每个线程有自己的 **TCB（Thread Control Block）**，记录标识符、寄存器、栈等现场
5. 同一进程内各线程**共享同一地址空间**
6. 一进程中的线程在**另一进程中不可见**
7. 同一进程内线程间通信主要**基于全局变量**

### 2.5.4 进程 vs 线程（工厂车间比喻）

> 名比喻：阮一峰的工厂模型
> - **CPU = 工厂**（一次只能供电给一个车间）
> - **进程 = 车间**（任一时刻 CPU 只在跑一个进程）
> - **线程 = 车间里的工人**（一个进程包含多个线程协作）
> - **进程内存 = 车间空间**（共享，每个工人都能用）

### 2.5.5 线程的分类（必考）

| 类型 | 关键特征 | 优点 | 缺点 |
|---|---|---|---|
| **用户级线程 ULT** | 仅存在于用户空间，**内核看不见**，资源仍按进程分配 | 切换开销小，可跨平台；可自定义调度算法 | 一线程阻塞可能导致**整个进程阻塞**；无法利用多核 |
| **内核级线程 KLT** | **由内核创建/管理/调度**，对所有用户进程可见 | 多核环境可调度多线程，**真并行**；并发度高 | 切换需"用户→内核→用户"模式切换，开销较大 |
| **混合式线程** | 两层都支持：用户层用 pthread 库管理 ULT，内核层支持 KLT | 兼顾灵活性与并行性 | 实现复杂；典型应用：窗口系统、大规模并行计算 |

## 2.6 进程互斥

### 2.6.1 并发进程的分类

> 有关 vs 无关
> - **无关并发进程**：没有共享资源，互不影响
> - **有关并发进程**：共享某些资源，可能互相干扰

### 2.6.2 与时间有关的错误——三个经典实例

#### 实例 1：飞机售票问题

**场景**：2 个购票进程 T1、T2，共享一个全局余票变量 Aj，X1 和 X2 是各自的局部变量。

**正确（串行）执行序列**：

```text
T1 完成后再 T2:
X1 := Aj;        (T1)   -- 读余票
X1 := X1 - 1;    (T1)   -- 减一
Aj := X1;        (T1)   -- 写回
[输出一张票]      (T1)
X2 := Aj;        (T2)   -- 读余票 (此时已是 Aj-1)
X2 := X2 - 1;    (T2)
Aj := X2;        (T2)
[输出一张票]      (T2)
-- 结果: Aj 减少 2, 票售出 2 张 ✓
```

**错误的交错执行序列**：

```text
X1 := Aj;        (T1)   -- T1 读到余票 N
X2 := Aj;        (T2)   -- T2 也读到 N (!)
X1 := X1 - 1;    (T1)   -- X1 = N - 1
Aj := X1;        (T1)   -- Aj = N - 1
[输出一张票]      (T1)
X2 := X2 - 1;    (T2)   -- X2 = N - 1
Aj := X2;        (T2)   -- Aj = N - 1 (!) 又一次写入相同值
[输出一张票]      (T2)
-- 结果: Aj 只减少 1, 但票售出 2 张 ✗ 多卖票!
```

> 后果
> 实际上只剩一张票，却被卖给了两位旅客。这就是航空公司"超售"问题在程序层面的来源。

### 2.6.3 临界区与临界资源

> 三个核心概念
> - **临界区**：并发进程中**与共享变量有关**的程序段
> - **临界资源**：共享变量所代表的资源
> - **相关临界区**：多个并发进程中涉及**相同共享变量**的那些程序段

### 2.6.4 互斥管理的三大要求（必考）

> 期末经常写"简述对临界区管理的三个要求"
> 1. **互斥进入**：一次最多让一个进程在临界区执行
> 2. **有限等待 / 有限退出**：进入临界区的进程必须**有限时间内退出**，不能赖在里面
> 3. **让权等待 / 不强迫等待**：有进程退出时应让等待者中的一个进入，不能让等待者**无限等下去**

### 2.6.5 信号量与 PV 操作

> 信号量 Semaphore
> 信号量 S 是一个**整数变量**：
> - **S ≥ 0**：可供使用的资源实体数
> - **S < 0**：正在等待该资源的进程数（绝对值）
>
> 信号量除赋初值外**只能通过 PV 操作访问**。

> 自习室类比：信号量 = 笔筒
> **信号量 S = 笔筒里有多少支笔**
> - S = 3 → 笔筒里有 3 支笔
> - S = 0 → 笔筒空了
> - S = -2 → 有 2 个人在等笔队列
>
> **P 操作 = 申请笔**：
> ```
> P(S): S = S - 1
>       if S < 0: 阻塞自己，去等笔队列
> ```
>
> **V 操作 = 归还笔**：
> ```
> V(S): S = S + 1
>       if S <= 0: 唤醒一个等待者
> ```

**PV 操作语义（原语，不可中断）**：

```text
P(S):
    S := S - 1;
    if S < 0 then W(S);    -- W(S): 阻塞调用者, 入 S 等待队列

V(S):
    S := S + 1;
    if S <= 0 then R(S);   -- R(S): 释放一个 S 等待者, 入就绪队列
```

> 三条推论（必考）
> 1. **S 为正值** → 等于实际还可用的资源数
> 2. **S 为负值** → 其绝对值 = S 等待队列中的进程数
> 3. **P = 请求资源 / 阻塞自己；V = 释放资源 / 唤醒别人**

### 2.6.6 用 PV 实现互斥的四步套路

> 套路必背
> 1. **设互斥信号量 S**，初值为 **1**
> 2. **找到临界区**（涉及共享变量的代码段）
> 3. **临界区前** 加 `P(S)`
> 4. **临界区后** 加 `V(S)`

**通用模板**：

```text
        进程 P                  进程 Q
        ......                  ......
        P(S);                   P(S);
        临界区;                 临界区;
        V(S);                   V(S);
        ......                  ......
```

## 2.7 进程同步

### 2.7.1 同步与互斥的区别

> 一句话区分
> - **互斥**：解决"**临界区只能一个进入**"的问题——竞争关系
> - **同步**：解决"**进程间按顺序协作**"的问题——合作关系
>
> 互斥是同步的特例，但同步比互斥多一层"消息传递"的语义。

### 2.7.2 经典问题 1：生产者—消费者（缓冲区容量 n）

> 推广要点
> - SP 初值改为 **n**（最多可同时存 n 个）
> - SG 初值仍为 0
> - 引入两个指针 **k**（存位置）和 **t**（取位置），都初值为 0
> - 缓冲区**循环使用**：`k := (k+1) mod n`

```text
SP, SG: integer;
SP := n;  SG := 0;
k := 0;   t := 0;
buffer[0..n-1];

生产者:                            消费者:
    while true do                      while true do
        生产物品 i;                        P(SG);
        P(SP);                             item := buffer[t];
        buffer[k] := i;                    t := (t+1) mod n;
        k := (k+1) mod n;                  V(SP);
        V(SG);                             消费 item;
```

> PV 顺序铁律（必考）
> **用于同步的 P 操作在前，用于互斥的 P 操作在后。**
> V 操作顺序无所谓。

## 2.10 死锁

### 2.10.1 死锁的概念

> 一句话定义
> **死锁 = 多个进程因竞争资源而陷入的一种僵局，若无外力作用，所有进程都将永远不能向前推进。**

### 2.10.2 死锁的四个必要条件（必背！必背！必背！）

> 期末必考
> **同时**满足以下四个条件，才可能产生死锁：

| 条件 | 含义 |
|---|---|
| **互斥条件** | 资源一次只能被一个进程使用 |
| **占有且等待条件** | 进程已占有部分资源，请求新资源被阻塞时**不释放已占有的** |
| **不剥夺条件** | 已获得的资源**不能被强行夺走**，只能由占有者自愿释放 |
| **循环等待条件** | 存在进程链 P₁ → P₂ → ... → Pₙ → P₁，每个进程都在等下一个进程占用的资源 |

### 2.10.3 死锁的四种对策

| 对策     | 思想                           | 何时启用    |
| ------ | ---------------------------- | ------- |
| **预防** | 限制资源请求，使必要条件在系统执行的！任何时间！都不满足 | 事前设计    |
| **避免** | 允许必要条件存在，但**分配前预测**是否安全      | 运行时每次申请 |
| **检测** | 不限制不预测，**定时运行死锁检测程序**找出死锁    | 运行时定期   |
| **解除** | 检测出来后**强制打破**死锁状态            | 检测到死锁后  |

### 2.10.4 死锁预防

破坏四个必要条件之一即可：

| 破坏条件 | 可行性 |
|---|---|
| 破坏**互斥** | 难——很多资源天然互斥 |
| 破坏**占有且等待** | **静态分配策略**——可行 ✓ |
| 破坏**不剥夺** | 仅适用于 CPU、主存等可剥夺资源 |
| 破坏**循环等待** | **层次分配策略**——可行 ✓ |

#### (1) 静态分配策略（破坏"占有且等待"）

> 思想
> 进程**执行前一次性申请所有需要的资源**，全部满足后才开始执行。期间不再申请。

| 优点 | 缺点 |
|---|---|
| 实现简单 | 资源利用率严重下降（很多资源全程被占却用不上） |

#### (2) 层次分配策略（破坏"循环等待"）

> 思想
> 资源分**多个层次**，规则：
> - 进程得到第 i 层的资源后，**只能再申请较高层**
> - 释放时**先释放较高层**
> - 申请同层另一资源前**必须先释放当前同层资源**

### 2.10.5 死锁避免——银行家算法

> 安全状态 vs 不安全状态
> - **安全状态**：OS 能保证所有进程在**有限时间内**得到所需全部资源
> - **不安全状态**：未必发生死锁，但**有可能**发生
>
> 系统**只要保持安全状态**就不会死锁。

#### 银行家算法本质

> 终极简化版
> | 角色 | 核心操作 |
> |------|----------|
> | **用户** | Need **(-)** → 0 → 归还 |
> | **银行家** | 比对 **Need ≤ Available** → Available **(-)** → Available **(+)** |

> 记忆口诀
> **用户减需求，减完就归还**
> **银行家三步：比对需求够不够、减资源池、加资源池**

**滚雪球思想**：先满足小需求进程 → 回收资源 → 资源池变大 → 再满足大需求进程 → **雪球越滚越大，最终全部完成**。

## 章末小结

> 一图带走第二章
> 处理器管理 = **多个进程争用 CPU + 共享资源时如何不打架、不饿死、不僵死**。
>
> | 阶段 | 核心概念 / 工具 |
> |---|---|
> | 抽象 | 进程（PCB）、线程（TCB） |
> | 调度 | FCFS / 优先数 / 时间片轮转 / 多级反馈队列 |
> | 互斥 | 临界区 + 互斥信号量（PV 初值 1） |
> | 同步 | 同步信号量（PV 初值 0 或 n） |
> | 高级抽象 | 管程（封装数据 + 操作） |
> | 通信 | 共享存储 / 消息传递 / 管道 |
> | 死锁 | 四必要条件 + 预防 / 避免（银行家） / 检测 / 解除 |
>
> **复习重心排序**：调度算法 ≈ 互斥同步 PV ≈ 死锁四条件与银行家 > 进程状态 / PCB > 线程分类 > 管程 > IPC。

### 必背套路

1. 进程**三态转换**图、五态扩展（必考）
2. 调度**七种时机**（必考填空）
3. **时间片公式** q = R / N，及"过短/过长"两难
4. **PV 实现互斥四步骤**：找临界区 → 设 S=1 → 前 P 后 V
5. **PV 实现同步**：信号量初值 = 缓冲区容量；多生产多消费时**同步 P 先于互斥 P**
6. **死锁四必要条件**："互斥 / 占有且等待 / 不剥夺 / 循环等待"
7. **银行家算法**：每次分配前模拟"滚雪球"找安全序列
8. **进程资源分配图**简化判定死锁的三条规则

### 高频陷阱

- 并发 ≠ 并行
- "等待 → 执行" 不存在
- 同步 P 在前，互斥 P 在后（写反 → 死锁）
- 哲学家进餐朴素 PV 方案会死锁
- 银行家算法关心的是**安全**，不是"会不会死锁"——不安全 ≠ 一定死锁
- 死锁检测：有环路 ≠ 一定死锁（除非每类资源数为 1）
